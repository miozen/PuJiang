## 已确认规则

| 主题 | 规则 | 依据 |
|---|---|---|
| 上下文 | 添加子女依据当前有效 PlacementId 及有效后代承接，人物资料目标为 PersonId；失效、跨谱或不匹配的位置不得自动替换。 | 编修 §1.4；交互 §2.3、§10.1；架构 §5.2 |
| 身份和空姓名 | 每个子女是独立真实 Person，位置有独立 PlacementId；空姓名人物也是实际人物，可有子女。主动添加空节点与取消普通姓名输入不同；后续补名保留 ID。 | 领域 §3.2.1、§6；编修 §4.1；交互 §6.2 |
| 姓名和默认性别 | 新增主线人物默认项目主姓氏，人物自身保存完整姓名；原位输入名字，按用户确认在前显示不可编辑姓氏；新增默认男性但可更改。 | 交互 §4.1、§6.3；D-029 |
| 父母事实 | 已知单方亲子关系允许成立，不为未知父母或配偶造人；生父、生母各最多一个已确认者，待考候选可多个；不同关系身份分离。唯一已确定配偶的新增默认遵守既定规则，不可仅据布局推断关系。 | 领域 §4.1–4.4、§5；交互 §6.4 |
| 承接和排行 | 普通生子通常在生父世系承接后代；最多一个有效后代承接位置。排行属于父子挂接位置，同一父节点男女分组、各组按长幼，新子女默认排对应组末尾；实际排行不覆盖历史行第。 | 领域 §7.1–7.2、§11.1–11.7；编修 §3.4 |
| 世代及房支 | 已记录显式世代不因新增关系而自动覆盖；D-026 允许为普通新子女草稿预填下一世、允许修改。房支起点以下后代默认继承，具体 Q-06 尚待细化。 | 领域 §10、§12.3、§18；D-004、D-026 |
| 提交与隔离 | 明确操作经 Application Command、Domain 校验和原子事务提交，人物、必要关系、位置及必要排行不得部分成功；失败保留输入，已提交后刷新失败须区分。重复提交不得重复创建。 | 架构 §6–8、§13；交互 §6.2、§7–8、§13.4 |
| 展示 | 投影从已提交事实生成对应节点和边；布局及画布不反向决定亲属事实。提交成功后选中新 PersonId + PlacementId；展开折叠和视图变化不写关系。 | 架构 §10–13；交互 §6.2、§10–11 |

## 冲突与待确认项

1. **多配偶默认生母：存在直接差异。** 编修 V1.0 §4.1 说多配偶不得擅自指定生母；交互 §6.4 禁止仅凭配偶顺序静默覆盖已确定生母，§6.5 对兄弟姐妹明确禁止仅凭配偶顺序推断；领域 §4.3 不允许仅凭配偶关系自动推断，但保留已确认的录入辅助规则。D-028 曾确认新增子女按当前图表第一位明确夫妻配偶默认，旧无图表路径还按 ID 选首位。V1.0 对已有子女的保护和新增时的默认不能混为一谈；以“新子女尚无生母”绕过编修 §4.1 也不成立。须请用户确认并按文档治理协调 D-028 与契约。待确认前，多配偶场景不套用旧默认。
2. **唯一配偶的具体范围与事实状态：** 交互 §6.4 允许唯一已确定配偶作为另一方父母默认，领域 §4.3 同时要求默认辅助不能代替明确事实。何谓“已确定”（夫妻／伴侣、对方未详、关系状态和角色不明）、默认是待确认还是直接形成已确认关系、从母亲位置新增时的对称处理，现有条文没有完整无歧义的执行定义；不得自行补齐。
3. **当前人物性别和父母角色：** V1 Person 尚无性别字段；首节点虽有新增主线默认男性的契约，但现有首节点未保存该属性。不能据姓名、位置或默认值追认既有首节点是生父；未知／不匹配角色与女性位置新增的处理需明确，不能默认为生父。
4. **位置与后代承接：** §1.4 明确依赖当前位置和有效承接，领域 §7.2 规定普通生子通常在生父世系承接；当前 V1 Placement 无父位置及承接状态。无效／非承接位置操作如何引导、母亲位置与生父位置如何对应，不能自动选择人物的其他位置。多位置、嗣继、祧继不在首个建议切片中猜测。
5. **关系状态与结构：** 领域 §5 定义待考／已确认／已否定，待考不自动进入正式投影，状态更改不自动创建位置；新增操作同时需要明确关系和位置。首条链路中明确录入父子关系的状态、事实确认动作及关系—位置关联须先确认，不能把“新增位置”本身当作关系证据。
6. **排行与性别未知：** V1 排行属于父子挂接位置，D-026 旧设计按图表保存显示顺序，两者范围不同，不能直接等同。新子女默认男性可按规则追加；已有未知性别成员、缺失排行及并发排序需要明确处理；Q-07 对迁移、删除和不完整旧谱仍待审查。
7. **空姓名条文表述：** 交互 §6.2 与领域 §3.2.1 明确允许主动添加空姓名真实人物；交互 §13.1 又写“不得保存无效的空姓名人物”。应将“无效普通输入”和主动空节点的边界列为契约协调项；在正式协调前不得把普通取消视为主动创建，也不能禁止契约明确允许的空节点。添加子女时是否提供带明确父位置的空节点入口及其操作流程需明确。
8. **世代与范围：** D-026 的下一世预填可用于新人物输入，不授权修改已有谱载世代；预填成为显式事实的确认时机、父世代缺失和异常提示待明确。当前 Person 无世代字段。D-004 的主动更正后代例外不等同于新增子女规则。
9. **旧模型及持久化：** 新库当前是按测试新建的隔离 SQLite，旧测试库无自动升级；Relationship、结构、排行和必要约束都尚不存在。新切片不能双写旧工作台、自动迁移旧库或访问真实数据。项目缺失姓氏、多位置房支、删除和恢复均不应靠新增子女补造规则。

## 建议的最小切片（待用户批准）

在**全新隔离数据库**中，用明确的虚构数据准备一个已有有效根位置、角色明确、没有配偶的父亲；用户从该位置主动新增一名普通子女。只讨论已记录单方生父关系、相应子女位置和其位置排行；不接配偶、多位置、嗣继、祧继、迁移或删除。输入可按已确认交互使用虚构项目姓氏、默认男性和自动提交。目标是贯通 Command → Domain → SQLite 事务 → 权威快照 → 投影节点／边 → 横向布局／隔离画布 → `PersonId + PlacementId` 焦点，而不是重写或替换旧工作台。

实施前仍须确认：①该单方关系由用户主动新增时的关系状态及位置／承接定义；②现有首节点尚无性别时如何取得明确生父角色（测试样本显式提供角色，还是先接入已确认的属性编辑能力）；③首批是否包含主动创建空姓名子女、世代预填及房支。测试样本不能暗示现有真实人物的缺失属性已经确定。
