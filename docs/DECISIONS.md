# 决策契约

状态含义：**Proposed** 为待确认方案；**Accepted** 为已确认且必须遵守；**Superseded** 为已被后续决策取代。改变 Accepted 决策需先获用户确认。

## D-001 — 产品与技术基线

- **状态：Accepted**
- **决策：** 谱匠（PuJiang）是完全离线的 Windows 原生单机族谱管理系统，技术栈固定为 .NET 10、WPF、EF Core 与 SQLite。
- **理由：** 兼顾本地数据控制、Windows 桌面体验和现有原型复用。
- **影响：** 不引入云端/服务器依赖；发布、测试和恢复流程按 Windows 本地软件设计。
- **相关：** `ZupuPaiBan/ZupuPaiBan.csproj`；[架构契约](ARCHITECTURE.md)。

## D-002 — 多族谱隔离

- **状态：Accepted**
- **决策：** 一个 SQLite 数据库管理多套独立族谱，以稳定族谱标识隔离所有族谱内数据；不限姓氏。
- **理由：** 让单机用户管理多套谱系，且保留统一备份与查询能力。
- **影响：** 目标数据模型的所有族谱内实体必须具有且查询时必须约束 `GenealogyId`；跨谱关系默认禁止。
- **相关：** [目标数据模型](ARCHITECTURE.md#target-数据与关系边界)。

## D-003 — 关系与人物记录原则

- **状态：Accepted**
- **决策：** 保留生父母、配偶、过继、嗣继、房支、失考等谱系信息，并允许为每种图表指定谱系展示主线。人物可有完整配偶档案，也允许信息不完整的历史人物记录。
- **理由：** 传统族谱资料存在关系多义性与缺失，不能压缩为单一父系字段或配偶姓名文本。
- **影响：** 人物、关系、婚姻/家庭和房支必须分离建模；“主线”是展示投影规则，不得覆盖原始关系。
- **相关：** [关系模型原则](ARCHITECTURE.md#target-数据与关系边界)。

## D-004 — 世代与排行的权威性

- **状态：Accepted**
- **决策：** 谱载世代与排行为人工权威记录；系统可提供自动推导参考值，但绝不自动覆盖原始谱载。
- **理由：** 真实谱牒存在跨支、继嗣和资料误差，自动结果不能取代史料。
- **影响：** 原始值、推导值、来源和人工确认状态应可区分。
- **相关：** [P0](CURRENT_PLAN.md#p0--开发基础与数据模型)。

## D-005 — 数据交换优先级

- **状态：Accepted**
- **决策：** 优先设计内部版本化 JSON；随后完善 Excel 和 GEDCOM 交换。
- **理由：** 内部格式才能无损表达领域关系，Excel/GEDCOM 是兼容层而非领域权威。
- **影响：** 导入导出必须版本化、可预检、可报告损失；不得以现有简化格式约束核心模型。
- **相关：** [P4](CURRENT_PLAN.md#p4--数据交换与谱书制作)。

## D-006 — 数据安全与演进

- **状态：Accepted**
- **决策：** 备份恢复、关系校验、事务和自动化测试在早期开发纳入范围；使用 EF Core Migration 管理数据库演进。
- **理由：** 族谱数据不可轻易重建，批量导入与关系修改必须可验证、可恢复。
- **影响：** 不能以 `EnsureCreated` 作为正式升级方案；破坏性导入必须预检与事务化。
- **相关：** [持久化策略](ARCHITECTURE.md#target-持久化安全与演进)。

## D-007 — 重建范围与架构尺度

- **状态：Accepted**
- **决策：** 当前没有需要保留的旧版 `FamilyMember` 数据库，P0 不实施该旧模型的数据迁移。保留有价值的 WPF 界面和功能原型，允许重新设计核心模型；避免微服务化、无必要多工程拆分和过度重构。
- **理由：** 现有原型的单父系模型无法承担目标领域，且无遗留数据约束。
- **影响：** 可在单桌面应用内渐进替换持久化与领域层，但须保留清晰模块边界。
- **相关：** [当前与目标边界](ARCHITECTURE.md)。

## D-008 — 传统吊线图细则

- **状态：Proposed**
- **决策：** 传统吊线图的地域谱式、具体版式模板及复杂关系的视觉表达尚未确认。
- **理由：** 这些规则直接影响布局算法、分页和验收样张。
- **影响：** 不得把现有“Vertical”树图等同于传统吊线图；P3 实施前须确认规则或提供样张。
- **相关：** [P3](CURRENT_PLAN.md#p3--传统吊线图)。

## D-009 — 项目名称、仓库与分支策略

- **状态：Accepted**
- **决策：** 项目中文名为“谱匠”，拼音/产品标识为 `PuJiang`；Git 远端为 `https://github.com/miozen/PuJiang.git`。`main` 为稳定分支，`dev` 为日常开发分支；需要隔离的较大功能使用 `feat/*` 分支。
- **理由：** 统一产品标识、仓库归属与跨电脑协作基线。
- **影响：** 新增产物、测试工程和程序集使用 `PuJiang`；现有 `ZupuPaiBan` 源码目录与命名空间暂作为渐进重命名范围，不能在无专项验证下机械替换。
- **相关：** [开发协议](../AGENTS.md)；[接力状态](HANDOFF.md)。

## D-010 — 工程质量、数据目录与发布基线

- **状态：Accepted**
- **决策：** 使用 `PuJiang.slnx`、.NET SDK 10.0.402、xUnit 和真实 SQLite 临时文件作为统一 Windows 开发入口；GitHub Actions 在 Windows runner 执行 restore/build/快速测试。正式数据位于 `%LOCALAPPDATA%\\PuJiang`，与程序目录分离；正式发布目标为 `win-x64` self-contained。
- **理由：** 让离线桌面软件具备可重复构建、可隔离验证和可维护的数据边界，而不引入云端或复杂平台。
- **影响：** 测试不得触碰用户目录或真实族谱数据；性能/UI 验收独立运行；正式结构变更仍须遵守 D-006 的 Migration 和备份要求。CI 配置完成不等于远端已通过。
- **相关：** [开发与运行规范](OPERATIONS.md)；[Windows 构建、测试与发布](ARCHITECTURE.md#windows-构建测试与发布)。
